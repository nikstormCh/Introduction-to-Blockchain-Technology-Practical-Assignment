# Шаг 1 проекта Proof-of-Prompt

Этот модуль фиксирует сообщения обязательствами, объединяет их деревом Меркла
и проверяет одно раскрытое сообщение относительно заранее сохранённого корня.
Java 21 достаточно для демонстрации и автономных тестов. Groq, Postman, Hardhat
и интернет для этого запуска не нужны.

## Запуск

В PowerShell перейдите в корень Spring Boot проекта и выполните:

```powershell
./mvnw.cmd test
java '-Dfile.encoding=UTF-8' '-Dstdout.encoding=UTF-8' -cp target/classes ee.ut.proofofprompt.proof_of_prompt.crypto.Demo
```

Первый запуск компилирует код и проверяет протокол. Ошибка завершает запуск с
ненулевым кодом. Флаг Java `-ea` не нужен: проверки выполняются всегда.
Второй показывает настоящее построение дерева с новыми случайными секретами.

Главные строки демонстрации:

```text
Messages: 3
Proof steps: 2
Original message: true
Changed message: false
```

Корень будет отличаться при каждом запуске: случайные значения создаются заново.
Это ожидаемое поведение. Для проверки повторяемости алгоритма тесты используют
отдельные фиксированные учебные значения.

## Что делает программа по порядку

1. `Demo.main` создаёт три сообщения: правило SYSTEM, инструкцию DEVELOPER
   и вопрос USER. Это пример входа, который позже соберёт сервис.
2. `CommitmentService.commit` назначает позиции 0, 1, 2 и создаёт для каждого
   сообщения свой секрет размером 32 байта через SecureRandom. Этот секрет
   не является ключом Groq или ключом подписи: он нужен для скрывающего обязательства.
3. `PromptMessage` проверяет поля и сохраняет их в неизменяемом объекте.
   Роль, позиция, текст и исходный секрет нужны для последующего раскрытия.
4. `CanonicalMessage.encode` превращает объект в строго определённые байты.
   Без одинаковых правил JSON разные программы могли бы получить разные хеши
   из логически одинаковых данных. Текст не обрезается и не нормализуется.
5. `Hashing.leaf` добавляет байт 00 и вычисляет SHA-256. Полученный 32-байтовый
   хеш — commitment, то есть обязательство, и одновременно лист дерева.
6. `MerkleTree` объединяет листья. `Hashing.node` хеширует байт 01 и два
   дочерних хеша. Левый и правый порядок имеет значение.
7. `request.disclose(1)` выбирает инструкцию DEVELOPER и выдаёт её вместе с
   доказательством включения. Остальные тексты и их секреты туда не входят.
8. `MerkleTree.verify` заново вычисляет обязательство раскрытого сообщения,
   поднимается по пути и сравнивает результат с заранее известным корнем.
9. Демонстрация меняет только текст раскрытого сообщения, сохраняя прежний
   секрет, путь и ожидаемый корень. Проверка возвращает false.

## Пример из трёх сообщений

```text
                    Root
                   /    \
                 P01     C2  ← вопрос пользователя
                /   \
              C0     C1
           SYSTEM  DEVELOPER ← раскрываем это сообщение
```

`C0`, `C1`, `C2` здесь — названия обязательств, а не реальные hex-значения.
`P01 = Node(C0,C1)`, `Root = Node(P01,C2)`.

Проверяющий получает текст DEVELOPER, его роль, позицию 1, исходный секрет и
два соседних хеша: C0 слева и C2 справа. Он вычисляет C1 сам, затем P01, затем Root.
Для получения C0 ему не нужен скрытый текст SYSTEM: достаточно самого хеша C0.
Аналогично вопрос пользователя остаётся закрытым.

## Где смотреть код

Основные классы лежат в `src/main/java/ee/ut/proofofprompt/proof_of_prompt/crypto`.

| Файл | Ответственность |
|---|---|
| PromptMessage.java | Данные одного сообщения, роли и проверка формата |
| CanonicalMessage.java | Однозначная запись конкретной схемы сообщения |
| Hashing.java | SHA-256, префиксы листа/узла, hex и байты |
| MerkleTree.java | Дерево, выдача пути и проверка включения |
| MerkleProof.java | Соседние хеши и направления |
| CommitmentService.java | Создание секретов, сборка запроса и раскрытие |
| Demo.java | Учебный пример, который можно запускать и изменять |

Тесты: `src/test/java/.../crypto/CoreTests.java`. `src/test/java/.../crypto/StepOneTest.java` —
адаптер к JUnit существующего Spring Boot проекта. `SPEC-v1.md` содержит точные
правила, `src/test/resources/step1-test-vectors.properties` — контрольные результаты.
В автономной копии модуля `tools/check_vectors.py` независимо проверяет значения на Python. Python нужен только
для этой дополнительной проверки, не для Java-приложения.

## Почему подмена обнаруживается

При изменении content, role, position или randomValue изменяются байты обязательства,
затем лист и пересчитанный корень. Совпадение с исходным корнем теряется, кроме
пренебрежимо малой возможности коллизии при принятых предположениях о SHA-256.
Проверка пути также учитывает его длину и направления для выбранной позиции.
Нечётные деревья делятся по наибольшей степени двойки, строго меньшей размера;
последний лист не дублируется.

Доверенный корень надо получить отдельно. Если нарушитель заменит сообщение,
весь набор хешей и выдаст новый корень за исходный, согласованное дерево пройдёт
проверку относительно нового корня. Поэтому на следующем шаге нужна подпись сервиса.

Число сообщений тоже должно прийти из доверенного контекста. Путь проверяет
совместимость с размером, но не всегда отличает все размеры: соседний хеш
не показывает внутреннее устройство ветви. На шаге 2 подписываем корень,
messageCount и requestId. Сам лист requestId пока не содержит — его связь
с конкретным запросом появится через квитанцию.

`true` здесь означает только включение сообщения в набор с известным корнем.
Это ещё не итоговый VALID проекта и не доказательство выполнения инструкции LLM.

## Что проверяют тесты

- Канонические байты, листья, промежуточные узлы, корень и путь примера из лекции.
- Каждую позицию и подмену текста в деревьях от 1 до 65 сообщений.
- Подмену роли, позиции, секрета, соседнего хеша и направления.
- Сокращённый, удлинённый и переставленный путь; неверный корень и несовместимый размер.
- Пустой запрос, неверный hex, неизвестные версии, роли и направления.
- Русский текст, emoji, управляющие символы, кавычки, переносы строк и Unicode.
- Новые секреты при повторном запросе, выбор раскрытия, неизменяемость данных.

Простая проверка разных секретов — контроль очевидной ошибки повторного
использования, а не доказательство качества генератора случайности.

## Продолжение в вашем Spring Boot проекте

Классы используют пакет `ee.ut.proofofprompt.proof_of_prompt.crypto` и не требуют
новых зависимостей. Позднее CommitmentService можно зарегистрировать как Spring bean.
HTTP-контроллер на шаге 1 не нужен: проверка выполняется тестами и Demo.

JUnit-адаптер StepOneTest запускает эти же проверки через Maven. Файл значений
для него располагается в `src/test/resources/step1-test-vectors.properties`.
После переноса запустите `./mvnw.cmd test` из корня основного проекта.
Demo можно запустить в IDE как обычный Java main.

Сейчас сообщения и секреты живут в памяти процесса. На шаге 2 добавляется
подписанная квитанция, на шаге 3 — сохранение исходных данных, на шаге 4 — вызов Groq.
Для нового запроса всегда создаётся новый набор секретов и новое дерево;
старые доказательства не перезаписываются. Срок хранения определяется позднее.
