# Формат обязательств и дерева Proof-of-Prompt v1

Реализована часть шага 1 из плана: обязательства сообщений, упорядоченное дерево,
построение пути и проверка одного сообщения относительно заранее известного корня.
Основа — лекция и `Desktop/blockchain/claude/spec.md`. Подпись, постоянное хранение,
LLM и блокчейн относятся к следующим шагам.

## Граница доказательства

Фиксируется окончательный упорядоченный список текстовых сообщений на входе
контролируемого сервиса. Клиент не должен самостоятельно назначать себе роли
SYSTEM или DEVELOPER: окончательный список формирует приложение. Этот модуль
принимает уже собранный список; авторизация и HTTP-вход появятся позднее.

`verify(...) == true` означает только соответствие выбранного сообщения корню.
Это ещё не итоговый статус VALID всего проекта. Здесь нет подтверждения того,
кто принял запрос, когда это произошло и выполнила ли модель инструкции.

## Поля сообщения

| Поле | Правило v1 |
|---|---|
| protocolVersion | Целое число 1; другие версии отклоняются |
| position | Неотрицательный Java int; для включения обязательно position < messageCount |
| role | SYSTEM, DEVELOPER, USER или ASSISTANT, регистр значим |
| content | Unicode-строка; пустая разрешена, null и непарные суррогаты запрещены |
| randomValue | Ровно 32 случайных байта, записанных 64 строчными hex-символами |

Число сообщений `messageCount`: 1..2147483647 в формате; фактический размер
ограничивается памятью, а будущий HTTP-вход должен установить практические лимиты.
Позиции при создании назначаются автоматически в порядке списка: 0..n−1.
Каждый вызов `commit` создаёт новые независимые случайные значения для ВСЕХ
сообщений, даже если их тексты повторяют предыдущий запрос. Используется
`SecureRandom.nextBytes`, без ручного предсказуемого seed.

## Однозначное кодирование

`C(message)` — UTF-8 без BOM от компактного JSON по RFC 8785 для фиксированной
схемы выше. Реализация НЕ является универсальным JCS-сериализатором.
Порядок ключей: `content`, `position`, `protocolVersion`, `randomValue`, `role`.
Между элементами JSON нет пробелов и переносов. Целые записываются десятичными
цифрами. Кавычка и обратная косая черта экранируются. Для управляющих символов
используются `\b`, `\t`, `\n`, `\f`, `\r`; остальные U+0000..U+001F записываются
как `\u00xx` со строчными hex-цифрами. Остальные символы сохраняются.

Пробелы ВНУТРИ content, CRLF/LF, регистр и Unicode-нормализация не меняются.
Например, `é` и `e` с отдельным комбинируемым акцентом — разные байты.
Обычная сериализация произвольного объекта Jackson не заменяет эти правила.

Публичного JSON-парсера пока нет: вход — типизированные Java-объекты. При добавлении
HTTP/импорта нужно отклонять неизвестные/повторные поля, неверные типы, дробные
позиции, неизвестные роли и версии до вызова криптографического ядра. Не следует
молча преобразовывать отсутствующее поле в пустую строку или позицию 0.

## Обязательство и внутренний узел

```text
leaf(message) = SHA256(0x00 || C(message))
Node(left, right) = SHA256(0x01 || raw32(left) || raw32(right))
```

Префиксы — ОДИН байт 00 или 01, а не текст. `raw32` декодирует hex в 32 байта.
Для внешнего представления хешей используется 64 строчных hex-символа без `0x`.
Лист уже является обязательством: второй раз его не хешируем при включении в дерево.
Разные префиксы различают лист и внутренний узел.

## Форма дерева

Пустой список запрещён. Для одного листа корень равен листу. Для n > 1 берём
наибольшую степень двойки k, строго меньшую n, и соединяем корни первых k
и оставшихся n−k листьев. Это форма дерева из RFC 9162, раздел 2.1.

```text
3: Node(Node(C0,C1),C2)
4: Node(Node(C0,C1),Node(C2,C3))
5: Node(Node(Node(C0,C1),Node(C2,C3)),C4)
```

Листья и пары не сортируются. Нечётный последний лист не дублируется.
Построение занимает O(n) хеширований, дерево в памяти — O(n) узлов.
Создание и проверка пути требуют O(log n) шагов; дополнительно при проверке
хешируются байты раскрываемого сообщения.

## Путь и проверка

Путь — список шагов `{hash, side}` от листа к корню. `side` указывает сторону
СОСЕДА: LEFT или RIGHT. Пакет шага 1 содержит один PromptMessage и MerkleProof.
Другие тексты и случайные значения в него не входят.

Для четырёх листьев раскрытие позиции 1 содержит шаги `(C0, LEFT)`, `(P23, RIGHT)`.
Проверяющий вычисляет лист из раскрытых полей, затем `Node(C0, leaf)`, затем
`Node(полученныйХеш, P23)` и сравнивает результат с ожидаемым корнем.

На вход verify передаются отдельно `expectedRoot` и `expectedCount` из заранее
зафиксированного контекста. Проверяются границы позиции, форма пути для этой позиции
и размера дерева, число шагов, направления, затем пересчитанный корень.
Некорректные поля объекта отклоняются конструкторами; несоответствие доказательства
в verify даёт false. Ошибки среды SHA-256 не маскируются под ложное доказательство.

Число листьев НЕ следует считать полностью доказанным одним путём: соседний хеш
не раскрывает внутреннюю структуру своей ветви. Некоторые разные размеры дерева
имеют одинаковый путь для выбранной позиции. Поэтому на шаге 2 `messageCount`
нужно подписать в квитанции наряду с `merkleRoot`, `requestId` и прочими полями.
Получать доверенное число из непроверенного пакета нельзя.

## Сохранение и следующие этапы

Сейчас данные живут в памяти процесса. Для повторного построения после перезапуска
нужны те же тексты, роли, позиции, версии и ИСХОДНЫЕ randomValue; это шаг 3.
Новые случайные значения не восстанавливают прежние обязательства.

Публичные тестовые значения из `test-vectors.properties` (в Maven-проекте —
`src/test/resources/step1-test-vectors.properties`) предназначены только
для воспроизводимых проверок. В реальных запросах секреты должны оставаться
закрытыми до раскрытия выбранного сообщения. Простые тесты уникальности не
доказывают качество генератора случайности.

На шаге 2 формат квитанции из исходного черновика связывает протокол, requestId,
modelId, merkleRoot, messageCount и сведения о принятии подписью Ed25519.
Канонизацию квитанции надо реализовать и проверить отдельно; CanonicalMessage
работает только с сообщениями. Для полного VALID потребуются последующие проверки
подписи, ожидаемого запроса и блокчейна.

## Источники правил

- RFC 8785: https://www.rfc-editor.org/rfc/rfc8785
- RFC 9162, 2.1: https://www.rfc-editor.org/rfc/rfc9162.html#section-2.1
- Java SecureRandom: https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/security/SecureRandom.html

77 фиксированных контрольных значений получены независимой реализацией на Python:
канонические байты, листья и корень примера лекции, промежуточные узлы, корни
деревьев размеров 1..65 и строка со всеми управляющими символами и Unicode.
Обычный запуск тестов только читает значения и никогда их не перезаписывает.
